# Code Style Guidelines

## Idioms
- "Keep It Simple, Stupid"
- Use existing code as much as possible
- Readability is the first priority when writing code
- Code style should be consistent across the project
- All code should be well-documented with docstrings in English
- Use plain English in docstrings and comments. Prefer natural phrases to compound modifiers joined by hyphens; preserve technical identifiers and literal paths.
- All variables should be meaningful, concise, and short
- Keep argument names and variable names consistent across the entire project (e.g., if Python uses `--step`, SLURM scripts must also use `--step`, not `--steps`)

## Domain Models
- Define domain entities and structured experiment inputs and outputs with Pydantic v2 `BaseModel`, following `src/domain.py` and `src/config.py`
- Validate external data and experiment configuration at boundaries, before inference or other expensive work
- Reject unknown experiment configuration fields with `ConfigDict(extra="forbid")` so misspelled parameters fail early
- Keep orchestration and computation in ordinary functions; do not create speculative model hierarchies or wrap every temporary value in a model
- Use Pydantic serialization for persisted domain records; preserve existing artifact schemas unless an explicit migration is agreed

## Evaluation
- Always provide a `--num_samples` argument to allow small-scale dry runs (e.g., ~50) before full evaluation; omitting it runs all instances
- For custom (non-official) eval implementations, separate each step (e.g., data loading, inference, scoring) into independent stages and verify each before proceeding
- After completing individual modules, assemble them in one entry point and use a `--step` argument to invoke each module independently (e.g., `uv run --locked python eval/<benchmark>/main.py --step preprocess`)
- Reproducibility is the first priority for evaluation
- Generate result tables and figures with Python scripts, not Jupyter notebooks

### Directory Structure

The layout below is the generic convention for model evaluations. This project's acquisition artifacts and frozen run settings live under `data/skill-pattern-mine/runs/{run_id}/`, following ADR 0019 and `docs/adr/README.md`; preserve that layout.

```
data/
└── {benchmark}/
    └── results/
        └── {model_name}/
            └── *.json / *.csv

eval/
├── {benchmark}/
│   └── ...
└── tables-and-figures/
    └── rq{n}-{type}.png / .csv
```

### Reproducibility Defaults
- Default random seed: `42` (set in config YAML)
- Default temperature: `0`
- Results stored as JSON or CSV under `data/{benchmark}/results/{model_name}/`
- Tables and figures are generated by Python scripts under `eval/{benchmark}/`, then written to `eval/tables-and-figures/`

### Run Records
- Give every new experiment run a unique `run_id`; repeated runs of the same configuration must have distinct identities
- Reuse an existing run ID only to resume or replay that run with its frozen configuration and sample bounds, following ADR 0019
- Persist the validated effective configuration before expensive work, including defaults, CLI overrides, seed, sample limit, and the selected model when applicable
- For new or extended runners, record the run ID, UTC start time, code commit and working tree status, lockfile hash, and dataset or model versions when available; mark unavailable values explicitly, including when the project has no Git metadata
- A commit does not capture uncommitted changes; preserve the relevant source snapshot for a run with uncommitted changes or mark it as not fully reproducible
- Link outputs to their run record and prevent silent overwrites; subsequent stages must explicitly identify the input run
- Exclude credentials from persisted records; local records belong with ignored results, while any tracking system must retain an explicit link to those results
- Existing acquisition records freeze configuration, cutoff, pilot mode, and sample bounds; they do not yet record all provenance fields above. These conventions do not imply that existing artifacts contain those fields
- Keep the current storage layout. Record an ADR before introducing a tracking dependency or changing persisted schemas or data layout; no external tracking service is required by these rules

## Configs
- All experiment configurations are managed in `configs/` using YAML format
- One YAML file per benchmark, named `{benchmark}.yaml`
- Use `configs/` as the single source of truth for experiment parameters
- Define conventional project paths in the entry point that uses them, relative to the project root derived from `__file__`; keep these paths out of experiment YAML
- Keep file selection through CLI options where a workflow needs different inputs or separate results; preserve existing artifact locations and historical snapshot compatibility as specified in ADR 0024
- For model evaluation workflows, define model lists only in YAML; scripts must not maintain a second model list
- Keep credentials and machine specific cache or storage roots in the environment, outside experiment YAML
- CLI options select the configuration and stage, plus backend or model where applicable; `--model` must select a model from the chosen YAML list
- Resolve defaults and explicit CLI overrides such as `--num_samples` into one validated effective configuration before execution; explicit CLI overrides take precedence over YAML for new runs
- Resuming a run must preserve its frozen settings; reject incompatible overrides instead of changing the saved run
- The example below applies to model evaluation; retain the existing acquisition and pilot schemas for this project
- Template:

```yaml
# configs/{benchmark}.yaml
dataset: org/dataset_name  # HuggingFace dataset path

models:
  api:  # official SDK model names
    - gpt-4o
    - claude-sonnet-4-20250514
  vllm:  # HuggingFace model IDs (vllm)
    - meta-llama/Llama-3-70B-Instruct

inference:
  temperature: 0
  seed: 42
  max_tokens: 4096
  # num_samples: 50  # uncomment for pilot run
```

## Data
- Benchmark run results are stored in `data/`
- Benchmark results are stored under `data/{benchmark}/results/{model_name}/`
- Datasets should be loaded from configured external sources (e.g., HuggingFace) instead of stored in the repository by default
- Large data files should be added to `.gitignore`

## Logging
- Use Python `logging` module, not `print`, for all non-tqdm output
- Log level: `INFO` for progress, `WARNING` for recoverable issues, `ERROR` for failures
- Log format: `%(asctime)s - %(name)s - %(levelname)s - %(message)s`
- SLURM stdout (`*.out`) captures all logs; no need for separate log files

## LLM API
- Supply API keys through environment variables in the active shell or job environment, never in code, config files, logs, or persisted run records
- Use provider official SDKs for LLM API calls, such as `openai`, `anthropic`, `google-genai`, and `mistralai`
- Model and inference parameters are read from `configs/` YAML files

## Scripts
- `scripts/` is for workloads that require dedicated SLURM job submissions
- Split by model type: `{benchmark}_vllm.sh` (GPU, vllm) and `{benchmark}_api.sh` (CPU, official SDKs), matching `models.vllm` / `models.api` in config YAML
- Scripts request SLURM resources and forward arguments to the Python entry point; model lists and inference settings come from the selected YAML
- For model evaluation, the Python entry point loads and validates YAML, then iterates over the selected backend's model list or runs the single configured model selected by `--model`
- Acquisition and pilot scripts use their existing entry points and schemas; do not add unused model or backend options

### Bash Script Template

Usage for model evaluation: `sbatch scripts/<benchmark>_<backend>.sh --config configs/<benchmark>.yaml --backend <api|vllm> --step <step>`; optionally add `--model <configured-name>`. Adapt resource directives to the workload and current cluster limits; omit GPU directives for CPU jobs.

```bash
#!/bin/bash

# --- Job ---
#SBATCH -J <job_name>                # job name
#SBATCH -p <gpu|cpu>                 # partition
#SBATCH -t 30:00:00                  # verify the partition time limit
#SBATCH -o %x_%j.out                 # stdout: <job_name>_<job_id>.out

# --- Resources ---
#SBATCH -N <n>                       # nodes
#SBATCH -n <n>                       # total tasks
#SBATCH -c <n>                       # cpus per task
#SBATCH --mem=<size>                 # memory per node
#SBATCH -G <n>                       # total GPUs
#SBATCH --gpus-per-node=<n>          # GPUs per node
#SBATCH -C <constraint>              # e.g., a100, h100
set -euo pipefail

# --- Main ---
uv run --locked python eval/<benchmark>/main.py "$@"
```

### Bash Style
- Always start with `#!/bin/bash` and `set -euo pipefail`
- Use `# ---` comments to separate sections: Job, Resources, Main
- UPPER_CASE for script-level constants, lower_case for local variables inside functions
- Quote all variable expansions: `"$VAR"`, `"${ARRAY[@]}"`
- Use `$(command)` for command substitution, never backticks
- Long commands use trailing `\` for line continuation, with arguments indented one level

## Pilot Experiments
- For every project, make sure to generate a small sample of data and run a pilot experiment script to verify the code and environment
- Use `--num_samples` for small-scale dry runs before full evaluation
